# Taskeeper — Design Spec

**Date:** 2026-09-20
**Status:** Approved for planning
**Scope:** v1 of a multi-user task management system (Notion-like, task-centric)

## 1. Purpose

Taskeeper is a self-hosted-on-Vercel task manager for small teams. It borrows Notion's
workspace/project structure and clean surface, but not its block engine. Tasks are
first-class rows in Postgres, not nested blocks, which keeps queries simple and the
board fast.

### Success criteria

- A new user can sign up, land in a workspace, and create their first task in under 60 seconds.
- A workspace owner can invite a teammate by email; the teammate accepts and sees the same projects.
- Dragging a card on the board persists immediately and never shows a stale column after reload.
- The app runs on Vercel's free tier and Neon's free tier with no connection-limit errors.

### Explicit non-goals for v1

Block editor, nested pages, custom per-project property schemas, calendar view, due-date
reminders, comments, activity log, realtime multi-cursor presence, mobile app, billing.
Each is deferred, not designed out — see §9.

## 2. Domain model

```
User ──< Member >── Organization (= Workspace)
                          │
                          ├──< Project ──< TaskStatus
                          │                    │
                          │                    └──< Task ──< TaskLabel >── Label
                          │                          │
                          └──< Label                 └──< Task (subtask, self-ref)
```

Organization is the workspace. better-auth's `organization` plugin already models
organizations, members, roles, and email invitations, so there is no parallel
`workspace` table. "Workspace" is the user-facing word; `organization` is the table name.

## 3. Schema

### 3.1 Tables owned by better-auth

`user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`.

These are generated by the better-auth Drizzle adapter. Do not hand-edit them; regenerate
when the plugin set changes. Roles on `member`: `owner`, `admin`, `member`.

### 3.2 Application tables

**project**

| column | type | notes |
|---|---|---|
| `id` | text PK | nanoid |
| `workspace_id` | text NOT NULL | FK organization.id, ON DELETE CASCADE |
| `name` | text NOT NULL | |
| `slug` | text NOT NULL | unique per workspace |
| `color` | text NOT NULL | token name, not hex |
| `archived_at` | timestamptz NULL | soft archive |
| `created_by` | text NOT NULL | FK user.id |
| `created_at` / `updated_at` | timestamptz NOT NULL | |

Indexes: unique `(workspace_id, slug)`; index `(workspace_id, archived_at)`.

**task_status** — board columns, per project

| column | type | notes |
|---|---|---|
| `id` | text PK | |
| `project_id` | text NOT NULL | FK project.id, CASCADE |
| `name` | text NOT NULL | |
| `color` | text NOT NULL | token name |
| `position` | text NOT NULL | fractional index |
| `is_done` | boolean NOT NULL DEFAULT false | drives `completed_at` |

Index: `(project_id, position)`.

A new project is seeded with three statuses: Todo, In Progress, Done (`is_done = true`).

**task**

| column | type | notes |
|---|---|---|
| `id` | text PK | |
| `workspace_id` | text NOT NULL | denormalized, FK organization.id, CASCADE |
| `project_id` | text NOT NULL | FK project.id, CASCADE |
| `title` | text NOT NULL | |
| `description` | text NOT NULL DEFAULT '' | plain text in v1 |
| `status_id` | text NOT NULL | FK task_status.id, RESTRICT — see note below |
| `priority` | enum NOT NULL DEFAULT 'none' | `none\|low\|medium\|high\|urgent` |
| `assignee_id` | text NULL | FK user.id, ON DELETE SET NULL |
| `due_date` | date NULL | calendar date, interpreted in the workspace timezone (§3.4) |
| `position` | text NOT NULL | fractional index within status |
| `parent_task_id` | text NULL | FK task.id, CASCADE — subtasks, one level |
| `completed_at` | timestamptz NULL | set when moved to an `is_done` status |
| `archived_at` | timestamptz NULL | |
| `created_by` | text NOT NULL | FK user.id |
| `created_at` / `updated_at` | timestamptz NOT NULL | |

Indexes: `(project_id, status_id, position)` for the board;
`(workspace_id, assignee_id, archived_at)` for "my tasks";
`(parent_task_id)` for subtask lookup.

**label** — `id`, `workspace_id`, `name`, `color`. Unique `(workspace_id, name)`.
Labels are workspace-scoped so they are reusable across projects. There is no separate
label-management screen in v1: labels are created inline from the task detail panel's
label picker (type a name that does not exist, press Enter) and renamed or deleted from
that same picker's overflow menu.

**task_label** — `task_id`, `label_id`, composite PK, both FKs CASCADE.

**workspace_settings** — one row per workspace, created with it.

| column | type | notes |
|---|---|---|
| `workspace_id` | text PK | FK organization.id, CASCADE |
| `timezone` | text NOT NULL DEFAULT `'Asia/Yerevan'` | IANA zone name |
| `week_start` | smallint NOT NULL DEFAULT 1 | 1 = Monday |

This is a separate table rather than extra columns on `organization` because §3.1 reserves
better-auth's tables for better-auth. Settings here are workspace-wide, not per-user.

**Note on `task.status_id` RESTRICT.** RESTRICT is what we want for the common case: a
user must not delete a board column that still holds tasks. But it collides with deleting
a project, where `task` and `task_status` both cascade and Postgres gives no ordering
guarantee between them. Project deletion therefore runs as an explicit transaction —
delete tasks, then statuses, then the project — rather than relying on the cascade.
Deleting a non-empty status is rejected in the service layer with a message offering to
move its tasks, so the RESTRICT is a backstop, not the user-facing error path.

### 3.3 Three decisions worth stating

**Denormalized `workspace_id` on `task`.** Tenant-scoped queries ("everything assigned to
me", "search this workspace") hit one index rather than joining through `project`. The
cost is that `task.workspace_id` must always equal its project's — enforced by writing it
only in the task-creation service, never accepting it from a caller.

**`position` is a fractional index string, not an integer.** Dropping a card between two
others computes a key between their two keys (`fractional-indexing` package) and writes
exactly one row. Integer positions would require rewriting every row below the drop.
Positions are scoped to `(project_id, status_id)`.

**`task_status` is a table, not a Postgres enum.** Board columns are per-project and users
rename and reorder them; an enum would need a migration for every rename.

### 3.4 Dates and timezone

The workspace timezone is `Asia/Yerevan` by default, stored per workspace in
`workspace_settings.timezone` and changeable by an owner or admin. Yerevan is UTC+4 with no
daylight saving, but the value is a stored IANA zone name rather than a hardcoded offset,
so a workspace in a DST zone works without a schema change.

Two kinds of time, handled differently:

**Instants** — `created_at`, `updated_at`, `completed_at`, session expiry. Stored
`timestamptz`, always UTC, never converted before storage. Converted to the workspace
timezone only at render time.

**Calendar dates** — `due_date`. Stored as a bare `date` with no zone. "Due 2026-09-21"
means that calendar day in the workspace timezone, not an instant. Storing it as a
timestamp would make a task due on the 21st display as the 20th for anyone reading it in a
different zone.

The consequence is that "today", "overdue", and "due this week" cannot be computed from
the server's clock. Vercel functions run in UTC, so between 20:00 and 24:00 UTC the server
is already on the next day in Yerevan. Every such comparison goes through a single helper:

```ts
// lib/dates.ts
todayInZone(tz: string): string        // 'YYYY-MM-DD' calendar date in that zone
isOverdue(dueDate: string, tz: string): boolean
formatInZone(instant: Date, tz: string): string
```

Overdue filtering in SQL compares against `todayInZone(ctx.timezone)` passed as a
parameter — never `CURRENT_DATE`, which would use the server's UTC day. Dates are rendered
server-side in the workspace zone so server and client markup agree; no client-side
`toLocaleDateString` on a date that the server already formatted.

Per-user timezone overrides are deferred (§9). Until then everyone in a workspace sees the
same day boundaries, which is the behaviour a co-located team wants.

## 4. Tenancy and authorization

The client never supplies `workspace_id`. Every request resolves it server-side:

```ts
// lib/session.ts
async function requireWorkspace(slug: string): Promise<WorkspaceContext>
// 1. read better-auth session; no session -> redirect to /sign-in
// 2. resolve organization by slug
// 3. assert an active `member` row for (user, organization); none -> 404 (not 403,
//    so a non-member cannot probe which workspace slugs exist)
// 4. return { userId, workspaceId, role }
```

Every function in `server/*/queries.ts` and `server/*/actions.ts` takes a
`WorkspaceContext` as its first argument and filters on `ctx.workspaceId`. This is the
single choke point for tenant isolation — one file to audit, one place for its tests.

Role rules for v1:

| action | owner | admin | member |
|---|---|---|---|
| create/edit/archive project | yes | yes | yes |
| create/edit/assign/move task | yes | yes | yes |
| invite / remove members | yes | yes | no |
| edit workspace settings (timezone, week start) | yes | yes | no |
| change member roles | yes | no | no |
| delete workspace | yes | no | no |

Deliberately flat: v1 has no per-project permissions. Anyone in the workspace can edit any
task in it.

## 5. Application structure

```
src/
  app/
    (auth)/
      sign-in/page.tsx
      sign-up/page.tsx
      invite/[invitationId]/page.tsx
    (app)/[workspaceSlug]/
      layout.tsx                      shell: rail + header
      page.tsx                        workspace home = my open tasks
      projects/[projectId]/
        page.tsx                      list view
        board/page.tsx                board view
      settings/
        members/page.tsx
    api/auth/[...all]/route.ts        better-auth handler
  db/
    index.ts                          drizzle client over @neondatabase/serverless
    schema/{auth,project,task,index}.ts
  lib/
    auth.ts                           better-auth server config
    auth-client.ts                    better-auth react client
    session.ts                        requireWorkspace, requireRole
    position.ts                       fractional index helpers
    dates.ts                          workspace-timezone date helpers
  server/
    projects/{queries.ts,actions.ts}
    tasks/{queries.ts,actions.ts}
    members/{queries.ts,actions.ts}
  components/
    ui/                               shadcn primitives
    board/                            Board, Column, Card, DragContext
    task/                             TaskDetailPanel, TaskRow, PriorityPicker
    shell/                            Rail, WorkspaceSwitcher, ViewTabs
```

`queries.ts` holds read functions called directly from server components. `actions.ts`
holds `"use server"` mutations. Components never import from `db/` — only through
`server/`.

### Mutation contract

Every action follows the same four steps and returns a discriminated union:

```ts
type Result<T> = { ok: true; data: T } | { ok: false; error: string };
```

1. `requireWorkspace` (and `requireRole` where §4 demands it)
2. parse input with a Zod schema colocated in the same file
3. write, scoped to `ctx.workspaceId`
4. `revalidatePath` the affected route, return `{ ok: true, data }`

Actions never throw across the server/client boundary. Expected failures (validation, not
found, forbidden) return `{ ok: false, error }` with a message safe to display. Unexpected
throws are caught at the action boundary, logged with the workspace and user id, and
returned as a generic "Something went wrong" — internal details never reach the client.

## 6. Interface

### 6.1 Tokens

One slate ramp, blue primary, green success. Declared as CSS custom properties on `:root`
and `.dark`, exposed to Tailwind v4 through `@theme`. Components reference token names
only; a raw hex in a component is a bug.

| token | light | dark |
|---|---|---|
| `background` | `#F8FAFC` | `#020617` |
| `card` | `#FFFFFF` | `#0E1223` |
| `foreground` | `#0F172A` | `#F8FAFC` |
| `muted` | `#F1F5F9` | `#1A1E2F` |
| `muted-foreground` | `#64748B` | `#94A3B8` |
| `border` | `#E2E8F0` | `#334155` |
| `primary` | `#2563EB` | `#3B82F6` |
| `primary-foreground` | `#FFFFFF` | `#0B1220` |
| `success` | `#059669` | `#22C55E` |
| `destructive` | `#DC2626` | `#EF4444` |
| `ring` | `#2563EB` | `#3B82F6` |

Measured contrast: body text 16:1 light / 18:1 dark; `muted-foreground` 4.7:1 light and
7.9:1 dark against their own surfaces. Both themes clear WCAG AA independently — dark is a
separate tonal set, not an inversion of light.

Theme switching uses `next-themes` with a blocking inline script so there is no flash of
the wrong theme. Default follows the system setting.

### 6.2 Typography

Plus Jakarta Sans, self-hosted through `next/font/local`. Self-hosting rather than the
Google Fonts CDN avoids a render-blocking third-party request and the layout shift that
comes with it.

Scale: 12 / 13 / 14 / 16 / 20 / 24 / 32. App chrome body is 14px for productivity density.
Form inputs and all mobile body text are 16px minimum so iOS does not auto-zoom on focus.
Line-height 1.5 for body, 1.25 for headings. Dates, counts, and any numeric column use
`font-variant-numeric: tabular-nums` so values do not jitter as they change.

### 6.3 Shell

```
┌────────────┬──────────────────────────────┬─────────┐
│ workspace ⌄│ Project · [List|Board] ⚲ ⇅ + │  task   │
│            ├──────────────────────────────┤ detail  │
│ ▸ Projects │                              │ slide-  │
│   · Website│        view content          │ over    │
│   · Mobile │                              │  480px  │
│            │                              │         │
│ ⚙ Settings │                              │         │
└────────────┴──────────────────────────────┴─────────┘
  256px rail        fluid
```

The rail is 256px, collapsible to a 56px icon-only rail, and becomes a Sheet drawer below
1024px. The active project is marked by font weight plus a left indicator bar, never by
color alone.

Task detail is a slide-over panel rather than a route push, so the board stays visible
behind it. The URL still syncs to `?task=<id>`: the panel is deep-linkable and the browser
back button closes it.

Spacing follows a 4/8 rhythm. Radii: 6px buttons, 8px cards and inputs, 12px panels.

Breakpoints: 375 / 768 / 1024 / 1440.

### 6.4 Board

Columns are 280px wide. Horizontal scroll is confined to the board container — the page
itself never scrolls sideways. A card shows title, labels, assignee avatar, due-date chip,
and subtask count.

Drag uses dnd-kit with **both** pointer and keyboard sensors. Keyboard: Space lifts,
arrows move between positions and columns, Space drops, Escape cancels, with an
`aria-live` region announcing each move. A board reorderable only by pointer is
inaccessible, so the keyboard path is a requirement of the feature, not an enhancement.

Dropping a card sends `(taskId, targetStatusId, beforeId, afterId)`; the server computes
the fractional key. Sending a precomputed position from the client would let two
concurrent drags collide.

### 6.5 Motion and state

Transitions are 150ms ease-out and animate `transform` and `opacity` only. Press feedback
is a 0.98 scale. Focus rings are 2px `ring` at 2px offset and are never removed.
`prefers-reduced-motion: reduce` drops card transitions to opacity alone.

Mutations use `useOptimistic`: the card moves the instant it is dropped. On failure it
returns to its original position and a toast appears with a Retry action. Toasts use
`aria-live="polite"` and do not steal focus.

The board renders skeleton columns while loading. Empty states carry an action — "No tasks
yet · Create one" — rather than bare text. Destructive actions (delete project, remove
member) require confirmation and use the `destructive` token with an icon, never color
alone.

## 7. Deployment

Vercel, with Neon as the database. Neon's serverless HTTP driver is used rather than a TCP
pool, because Vercel functions are short-lived and a TCP pool would exhaust connections
under concurrency.

Environment variables: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`,
`RESEND_API_KEY`, and OAuth client id/secret pairs. `TZ=UTC` is set explicitly so the
runtime clock is unambiguous and every zone conversion is forced through `lib/dates.ts`.

Migrations are generated by `drizzle-kit generate` and committed. They are applied by an
explicit `drizzle-kit migrate` step in CI before the Vercel deploy promotes, not at
runtime on first request — a runtime migration on a serverless cold start can run
concurrently in several instances.

Preview deploys run against a Neon branch so preview data never touches production.

## 8. Testing

Vitest covers `server/*` against a real Postgres — a local container in development, a
Neon branch in CI. Not a mock: the tenancy guarantees in §4 are enforced by SQL, so a
mocked database would test nothing that matters.

The first tests written are the authorization boundary ones, and each asserts a negative:
a member of workspace A cannot read, update, or delete anything in workspace B through any
exported server function. Alongside those: fractional position ordering (including
repeated inserts between the same neighbours), `completed_at` set and cleared as a task
crosses an `is_done` status, and cascade behaviour on project deletion.

Timezone gets its own tests, run with the process clock pinned to UTC: a task due today in
Yerevan must not read as overdue when the server clock has already rolled past midnight
UTC, and `todayInZone` must return the Yerevan date, not the UTC one, at 21:00 UTC. This
is the class of bug that only appears in production between 8pm and midnight UTC, so it is
tested rather than observed.

Playwright covers one full path end to end: sign up, create workspace, invite a second
user, accept as that user, create a project, create a task, drag it across columns, reload
and confirm the new column persisted. Plus a keyboard-only run of the same drag.

Development follows TDD — test first, watch it fail, then implement.

## 9. Deferred

In rough order of likely value: comments and activity log; rich-text task descriptions;
calendar view with Vercel Cron reminders; saved filters and views; full-text search;
custom per-project properties; per-user timezone overrides; realtime sync; public share links; mobile app against a
REST layer reusing the same `server/*` functions.

The schema above does not block any of them. Comments and activity are additive tables.
Rich text replaces `task.description` text with a JSON column. Custom properties add a
`project_property` / `task_property_value` pair without touching existing columns.
